# Contributing

## Development setup

```bash
git clone https://github.com/Xtley001/optimal-sizing.git
cd optimal-sizing
cargo build --workspace
```

No system dependencies beyond a standard Rust toolchain via [rustup](https://rustup.rs). `sizing-core` and `sizing-bench` need no network access; `sizing-integration` needs outbound HTTPS to an Ethereum RPC endpoint at runtime (not at build time).

## Before opening a PR

```bash
cargo build --workspace
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```

All three must pass clean — this is exactly what `.github/workflows/ci.yml` runs on every PR. See [`docs/TESTING.md`](./docs/TESTING.md) for the full per-suite test command list and the testing contract this project follows (fixed regression values generated by running the code, proptest coverage per curve, no invented numbers).

## Code style and project rules

This project follows a strict "don't invent, don't assume" discipline: every numeric constant, formula, and tolerance must trace back to [`docs/API.md`](./docs/API.md), [`docs/whitepaper.md`](./docs/whitepaper.md), or [`docs/ARCHITECTURE.md`](./docs/ARCHITECTURE.md); no `f32`/`f64` anywhere in `sizing-core`'s public interface or internal math (`rust_decimal::Decimal` throughout); no mock or hand-estimated numeric test values. If you're adding a formula or constant that isn't already specified in one of those documents, add it there as part of your PR, not just in code comments.

## Pull requests

- Looking for something to work on? See [`ROADMAP.md`](./ROADMAP.md) for a prioritized list of what's genuinely still proposed (streaming/`--watch` mode, a historical backtesting harness, and the Tier 3 items), each with the reasoning for why it fits this project's architecture and, where relevant, why it hasn't been attempted yet. See [`CHANGELOG.md`](./CHANGELOG.md) for what's already built (multi-hop routing, concentrated liquidity, Multicall batching, language bindings, and more).
- Keep PRs scoped to one module or concern — this project was originally built one curve/component at a time and stayed easier to review for it.
- Update the relevant doc (`docs/API.md`, `docs/ARCHITECTURE.md`, or `docs/whitepaper.md`) in the same PR as any code change that affects a public signature, formula, or documented behavior — not as a follow-up.
- Add or update tests per [`docs/TESTING.md`](./docs/TESTING.md)'s coverage expectations: every public function needs at least one direct test, and every `SizingError` variant needs a test that triggers it specifically.

## Reporting issues

Use GitHub Issues. For security-relevant reports, see [`SECURITY.md`](./SECURITY.md) instead of opening a public issue.
